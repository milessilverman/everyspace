## 3. Suspected (not reproduced)
1. `calendar-feed/index.ts:66` exports only [space, direct parent, direct children]. It leaves out grandparents, grandchildren and `space_relations` blockers, which `blocking_spaces` counts (the DB side was shown in `S/c_door.mjs` C4; the Deno query was not run). If so, a house booking never closes a room-in-wing on Airbnb.
2. `ical.ts:97` labels any SUMMARY matching "not available|blocked|closed" as `block`, and blocks are excluded from conflict flagging. If a site exports real reservations that way (Booking.com is reported to use "CLOSED - Not available"), its double bookings would never be flagged. This needs a check against the official export format (network is blocked here).
3. `can_book` (`availability.sql:149-157`): on hosted Supabase, `postgres` is not a superuser, so `create_booking`, `import_reservations` and `place_hold` run from the SQL editor or a direct `postgres` connection are refused. No current caller does this.
4. The iCal `summary` (160 characters) is stored and can contain guest names on some sites, so personal data is persisted from feeds. The CSV path drops it correctly.
5. `booking-import` checks size only against the declared `content-length`. A chunked multipart body is read fully by `req.formData()` before the 1 MB check.
6. `fetch.ts`: `https://localhost../` passes the name check, and when `Deno.resolveDns` is absent (resolver null) it relies on the runtime's resolver. `[100::1]` and `[2001:10::1]` are allowed (non-routable, low risk).
7. `regulatory.js`: a generic (jurisdiction-less) `allow` rule decides `feasible`/0.8 when the only location-level rule is `require` (shown with a fixture in `S/d_revenue.mjs` D5). No such generic rule exists in the data today.
8. `FEE_CONFIDENCE = 0.3` with source "index.html PLATFORMS…" breaks the STATE hard rule (uncited means confidence <= 0.2 and source "Everyspace planning default (uncited)"). The method doc §2 says 0.3, so the doc and the rule disagree.
