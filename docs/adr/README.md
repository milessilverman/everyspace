# Architecture decision log

One row per decision. Status: accepted unless stated. Date: 2026-11-24.

| # | decision | context | alternatives rejected | consequences |
|---|---|---|---|---|
| 1 | Keep the stack: Supabase Postgres + Deno edge functions, static pages on GitHub Pages, `node --test`, no build step | Working backend with 34 tests and a live Host Console already exist; cost is $0 | New framework / bundler (rebuilds working code, adds cost and risk) | New code must run without a build; TypeScript only where Node can strip types |
| 2 | Domain logic lives in `/core` as zero-dependency ES modules with JSDoc types | The same estimate must be computed in the browser (free estimator), in tests and later in edge functions | TypeScript + bundler (build step, committed artefacts drift); logic inside `index.html` (untestable, 1.4 MB) | One implementation of every formula; `index.html` still has older copies until it is moved over |
| 3 | The database is authoritative for bookings; `core/availability.js` mirrors the rules | Race safety needs a transaction, a lock and a constraint; previews and the optimizer need the same rules without a round trip | JS-only checks (no race safety); SQL-only (no offline preview) | Two implementations, kept equal by a parity test over shared cases |
| 4 | Tenant = organization; roles are rows; `host_id` kept | Teams, co-hosts and cleaners need scoped access; the Host Console writes `host_id` today | Keep single-user tenancy (blocks multi-user); drop `host_id` (breaks the console) | Every policy goes through membership helpers; a personal org is created per user |
| 5 | Platforms and categories are lookup tables, not enums | New marketplaces and space types must not need a schema change | Keep the Postgres enum (needs `ALTER TYPE` per platform) | One-time type conversion of six columns; adding a platform is an `INSERT` |
| 6 | Provider adapters declare capability levels L0-L4 and omit what they cannot do | iCal is availability only; the demo overclaims "live everywhere" | A uniform interface with stubbed methods (hides what is not real) | UI and guard can state honestly what each connection does |
| 7 | Provenance on every attribute; append-only history; owner-confirmed wins | Accuracy rules; automated sources are incomplete and sometimes wrong | Overwrite in place (loses source and owner corrections) | More rows; a view resolves the current value |
| 8 | Reuse City Pretty by re-implementing its parcel-lookup pattern at a pinned commit, not by calling its Worker | The Worker has no parcel route, no auth, and admits Everyspace's origin only by accident | HTTP dependency on another project's unversioned Worker | No runtime coupling; registry entries copied as data; licence question A3 open |
| 9 | Restricted third-party data is isolated in `provider_data` with mandatory expiry | Verified: Airbnb's API terms bar "retaining static copies or building databases" and competing use (`docs/integrations.md`) | Storing API data in core tables | API data can be purged per provider without touching Everyspace records; never feeds estimates or aggregates |
| 10 | The optimizer searches feasible combinations exhaustively (max 20) | Earnings from spaces that share a home, yard or driveway cannot be added up | Sum of all opportunities (overstates); greedy (can miss the best set) | Exact and explainable for realistic property sizes; larger sets are refused, not approximated |
| 11 | Unsourced numbers are allowed only as labelled planning defaults with confidence <= 0.2; missing inputs are `unavailable` | No licensed comparable-data source exists yet | Hide the estimator until data is licensed (no product); present defaults as market data (misleading) | Every estimate today is "low confidence" by construction until owners enter their own figures or data is licensed |
| 12 | Staging is local Postgres 16 plus PGlite | The only hosted project is live, on the free plan, with no branches | Test on production (unsafe); paid branching (needs approval) | Vault, pg_cron and pg_net are not exercised in staging; listed as a production-apply check |
| 13 | External bookings are recorded even when they conflict; only Everyspace-originated bookings are rejected | A marketplace booking is a fact that already happened | Rejecting imports that overlap (hides real double bookings) | Conflicts table and alerts are the safety net for imported data; the exclusion constraint covers only `exclusive` rows |
| 14 | In the browser the estimator geocodes with Nominatim; server-side order is Census then Nominatim | Verified: the Census geocoder sends no CORS header; Nominatim allows cross-origin reads but limits the whole application to 1 request/second and forbids autocomplete | Browser calls to Census (blocked); a geocoding proxy now (needs a deploy to production) | Acceptable only at small volume; a cached server-side geocoder is required before any promotion of the estimator |
| 15 | A relation between two spaces means mutual exclusion in either arrival order | Review finding: with directional blocking, booking the pool then the lawn was accepted while the reverse order was refused | Directional relations (order-dependent outcomes) | One meaning everywhere (SQL, JS mirror, holds, instant-site rule); relations are not transitive and not inherited by child spaces |
