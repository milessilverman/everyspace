# Swimply read-only calendar plan

Verified November 20, 2026 Pacific time using the public provider documentation. The proposed first trial observes busy time in a calendar controlled by a consenting host. Booking acceptance, availability changes, cancellations, payouts and guest contact remain with the host on Swimply.

## What the documented connection provides

Swimply documents two-way iCal and a separate Cronofy setup under **Calendar → Availability → Sync external calendars** on its website. Swimply says iCal imports can take several hours and exports may take up to 24 hours to appear in an external calendar. Its Cronofy option is described as faster and puts Swimply bookings and the host’s selected buffer on the connected calendar. The published instructions provide no end-to-end delivery guarantee to Everyspace. They also describe bringing events back into Swimply from the connected calendar. Keep the dedicated calendar free of unrelated events and give Everyspace read-only access. [Swimply calendar documentation](https://swimply.zendesk.com/hc/en-us/articles/30133735282451-Syncing-Calendar)

An opted-in host can use the documented calendar connection. Before Everyspace reads the connected calendar, confirm with Swimply that the proposed downstream use, listing mapping and data retention are permitted for the pilot. Host consent and a separate calendar authorization are both needed. The Swimply connector does not issue Everyspace an API key or permission to read reservation details or change availability. Written approval would be needed for that scope. [Swimply terms](https://swimply.com/termsandconditions) · [Swimply Support](https://swimply.zendesk.com/hc/en-us/requests/new)

## Fastest path to test

1. **Use an isolated calendar the host owns.** Ask the host to connect a new, empty calendar dedicated to the pilot pool through Swimply’s documented Cronofy setup. Verify that Swimply selects just that calendar and identify the data and live availability side effects of connecting it. Measure that leg first in the host dashboard with consent. If the pool feed or supported account selection cannot be isolated, use the documented iCal export or verified manual entry until Swimply clarifies it. [Swimply calendar documentation](https://swimply.zendesk.com/hc/en-us/articles/30133735282451-Syncing-Calendar)
2. **Try native read-only notifications for the calendar.** For a supported Google Calendar connection, use the dedicated owner account and request `calendar.events.owned.readonly`, with exactly one calendar ID allowed in Everyspace. Register an HTTPS watch for that calendar when approved. Treat the channel notification as a wake-up signal. Verify the configured channel, resource and opaque token, then fetch current data with the separate OAuth grant. Renew the channel before expiry and retain a 15-minute fallback refresh. Google documents a default channel lifetime of seven days and says delivery can be missed. Test revocation and OAuth refresh-token expiry, including the seven-day expiry for many external apps in Testing. [Watch endpoint](https://developers.google.com/workspace/calendar/api/v3/reference/events/watch) · [Push notification precautions](https://developers.google.com/workspace/calendar/api/guides/push) · [Calendar scopes](https://developers.google.com/workspace/calendar/api/auth) · [OAuth verification](https://developers.google.com/identity/protocols/oauth2/production-readiness/sensitive-scope-verification)
3. **Normalize busy observations before touching occupancy.** Limit each read to the authorized calendar and pilot window. Drop names, titles, emails, descriptions, prices and attachments. Map stable calendar event IDs and provider revisions when available. Coalesce duplicate wakes, complete all pages before publishing, and retry transient failures with backoff. A timeout, changed cursor, partial page, moved event, or missed delivery should preserve previously verified occupancy until reconciliation. Google documents incremental tokens and a full resync after a `410 Gone`. An event disappearing from a mirrored calendar requires direct host verification before releasing an observed Swimply booking. Compare Swimply’s published buffer to local cleanup so the same period is not applied twice. [Google incremental sync](https://developers.google.com/workspace/calendar/api/guides/sync) · [Swimply calendar behavior](https://swimply.zendesk.com/hc/en-us/articles/30133735282451-Syncing-Calendar)
4. **Keep a separate Cronofy API as a fallback evaluation.** If the native calendar path is unavailable, request permission for an Everyspace application and a separate host calendar grant. Start with free/busy access if it preserves enough provenance. When stable event IDs are needed, request only the calendar read scope and discard all extra fields. Cronofy documents signed webhook notifications, an initial-sync state, and event read limits of 42 days in the past and 201 days ahead. Calendar change notices, deletion flags and a completed initial sync describe the calendar connection. The host dashboard remains the authority for a booking cancellation. [Calendar access](https://docs.cronofy.com/developers/authorization/access-modes/) · [Calendar webhooks](https://docs.cronofy.com/developers/push-notifications/) · [Initial sync state](https://docs.cronofy.com/api-reference/fundamentals/identity/userinfo/) · [Event window and incremental reads](https://docs.cronofy.com/api-reference/calendar-control/calendar-events/read-events/)

No Swimply latency measurement exists yet for Everyspace. A push-assisted calendar read should remove Everyspace’s own scheduled-poll wait when the notification is delivered. The first Swimply-to-calendar hop and missed or delayed notices still dominate the end-to-end result. Measure from a host-verifiable provider timestamp through calendar appearance to committed Everyspace observation. The pilot target is **p95 within five minutes** for at least 20 consented labeled changes, with every missed notification recovered by the next successful fallback read. Report median, p95, maximum, sample size, missed signals and any unmatched observations. Treat five minutes as a go/no-go target. Continue manual verification if the sample is too small or the target is missed.

## What this draft implements

Everyspace now collects bounded, complete calendar observations before applying them under the existing lease and property lock. The active iCal reader uses that path. Tests verify replayed pages, conflicting observations, interrupted pages, expired attempts and recovery with synthetic data. The console shows stale, failed, and incomplete reads, and distinguishes possible duplicates from confirmed conflicts. The draft contains no live Google, Cronofy or Swimply callback, credentials, calendar-writing client, or provider booking operation. [Staging verification and pilot runbook](STAGING_PILOT.md)

## Dedicated Google Calendar test proposal

Keep the test in a separate Google OAuth project in Testing with one approved synthetic or owner-controlled account. The proposed scope is `https://www.googleapis.com/auth/calendar.events.owned.readonly`. The test application would allow one explicitly configured dedicated calendar ID. An owned-calendar scope can cover other calendars the account owns, so use an account dedicated to the trial. Record the exact HTTPS redirect URI and consent text for approval once the protected preview exists. The proposed browser callback path is `/oauth/google/callback`. The Calendar watch route needs its own HTTPS endpoint and notification-channel validation. No OAuth client, redirect or watch is enabled by this draft. [Google Calendar scopes](https://developers.google.com/workspace/calendar/api/auth) · [Google Calendar push](https://developers.google.com/workspace/calendar/api/guides/push)

Before connecting, get separate approval for that scope, the exact browser callback and notification URL, the dedicated account and the consent text. Describe the busy intervals collected, the one-calendar restriction, retention and revocation. Store tokens only in staging and stop the notification channel and revoke credentials at the end. Verify with Swimply that its documented calendar connector can be used for this downstream test. [Swimply calendar connection](https://swimply.zendesk.com/hc/en-us/articles/30133735282451-Syncing-Calendar)
