## Access and onboarding

### Airbnb

1. Sign in with an Airbnb account representing Everyspace and start at the Partner Portal. Use Partner Support to request routing to the Homes Connectivity team as a new property management software or channel manager provider. If Partner Support requires a partner account you do not yet have, contact Airbnb Support and ask for the same routing. The public materials leave intake availability, minimum inventory and startup eligibility unconfirmed. [Partner Portal](https://www.airbnb.com/partner/) · [Partner Support](https://www.airbnb.com/partner/support) · [Airbnb Support](https://www.airbnb.com/help/contact-us)
2. Provide Everyspace's legal company name, website, contact, planned host inventory and markets, a product demo and its reservation and availability workflow. Ask for the current intake requirements, sandbox access, and approval for reservation and pending-request reads or events, request accept and decline, readback, and availability read, write, and synchronous checks. Ask what can be automated per listing and which certification and mandatory features apply. The request lists desired capabilities. Airbnb assigns the actual scopes. [Airbnb API terms](https://www.airbnb.com/help/article/3418) · [Partner sandbox guide](https://developer.withairbnb.com/homes/docs/sandbox-v2-partner-testing-environment-guide)
3. Complete the agreement and review process Airbnb specifies. The published terms require the mutual NDA, API terms, applicable partner terms, a security review, and implementation of mandatory features within six months of release. Airbnb may request a representative demo account. Obtain the written scope and test credentials before implementing or testing the live transport. [Airbnb API terms](https://www.airbnb.com/help/article/3418)

### Vrbo

1. As a software vendor, email **vrboconnectivity@expediagroup.com**, the address published by Integration Central for new Property Management Software companies. Introduce Everyspace and include its legal entity, website, supported markets, projected connected listings, and booking and availability model. Ask for the current criteria for a new provider and access to the supply-side Integration Central documentation and test tools. Vrbo publishes a vendor intake route. Acceptance, minimum volume and certification requirements depend on its review. [Integration Central](https://integration-central.vrbo.com/t)
2. Once invited, use **Request Access** in Integration Central. Confirm the required listing and availability feeds, real-time availability and booking callbacks, reservation lookup and updates, request acceptance, change notifications, supported authentication, payments responsibilities, and required certification tests. Include questions about event acknowledgment, rate limits, ambiguous outcomes, and exact property and reservation identifiers. Host account integration for an already-certified PMS is a separate process. [Integration Central](https://integration-central.vrbo.com/t) · [Vrbo software integration](https://help.vrbo.com/articles/About-Vrbo-integration)

Use the provider's documented sandbox and certification workflow to verify a whole round trip before considering a pilot. Credentials belong in server-side secret storage. Keep each listing's authorization and automation opt-in in the service-managed `channel_api_listings` table.

## Implemented in Everyspace

- Airbnb and Vrbo use separate adapter entry points and a shared contract. Both ship with disabled transports. Test fixtures use synthetic accounts, signatures and results.
- A provider adapter verifies the untouched webhook body and normalizes an account, listing, delivery ID and request ID. Durable intake checks that mapping and deduplicates deliveries before acknowledging them. The webhook wakes a worker. The worker retrieves current provider state, so a delayed delivery cannot apply an older state from its payload.
- The decision engine gives new requests a three-second collection window. It ranks known overlapping requests by expected host net proceeds in the same currency, then receipt time and request ID. Missing or incomparable competing quotes need review. Requests arriving after an approval begins cannot displace it.
- PostgreSQL uses the existing per-property transaction lock and related-space checks. It evaluates half-open stay ranges, manual holds and recorded reservations, direct availability for all known relevant external listings, and instant-book mode. It requires availability checks made within 20 seconds. In-flight and uncertain provider approvals make the dates unavailable to both the manual guard and other automatic approvals. Unrelated spaces remain independent.
- Only an authoritative, identity-checked provider read with a reservation reference and dates creates a confirmed calendar booking. A failed or ambiguous command gets read-only reconciliation with backoff. Unknown outcomes keep their hold after the worker lease or retry budget expires. An authoritative terminal state releases it. A new provider event can restart reconciliation. The existing conflict detector records provider confirmations that arrive independently without canceling any booking.
- The Host Console shows direct authorization, whether automatic approval is supported and enabled, iCal status, reservation status and reason, and alerts for host follow-up. Requests and decision history are restricted to the host's own spaces. The worker and intake RPCs are service-only.
- The existing 15-minute iCal pull and outbound feeds continue as the calendar fallback. Imported rows can block approval. An iCal read, fresh or stale, cannot supply authoritative availability or confirm an API request. Where the provider supplies an exact, verified iCal UID, API confirmation takes ownership of that calendar row and iCal cannot overwrite or cancel it.

The authenticated `POST /functions/v1/channel-reservations/process` route processes due work with a dedicated `CHANNEL_RESERVATION_WORKER_SECRET`. An approved rollout also needs a periodic invocation of that route to recover interrupted workers and process delayed retries. This branch adds the route and database state. Deployment, scheduling and production opt-in are separate steps after provider validation.

## Remaining risks

- A provider or host can confirm outside Everyspace between the availability read and the approval write. V1 holds automatic approval for known independently instant-bookable external listings and requires fresh direct coverage for active external listings. Keep provider listing inventory complete. Even with direct coverage, only a verified provider-side admission and commit contract can close that race.
- The runtime recovery path holds inventory when the provider stays unreachable, returns contradictory data, or lacks a terminal state. Operators need a verified provider response and then a reconciliation run. Expiring such a hold on a local timer could allow a second approval.
- The decision window ranks requests already received. Network delivery delays can surface a higher offer after the selected request is in flight. Automatic selection applies to single-unit inventory with comparable quotes. The engine leaves other requests for host review and can track a verified provider decline, expiration, or cancellation.
- iCal updates can arrive late or without a stable common ID. A calendar record and an API record can appear as a conflict until an operator can establish their identity. The engine matches stable IDs and keeps both records when identity is uncertain.
- Provider-specific status mapping, signature verification, idempotent writes, availability publishing and real-time booking callbacks still need approved sandbox validation. No provider cancellation operation is part of the automatic approval workflow.

## Local validation

From `platform/`, run `npm ci` and `npm test` for the provider fixtures, reservation engine, RLS, and existing platform suite. Run `npm run test:concurrency` with Docker for separate PostgreSQL sessions. The second suite creates its own disposable Postgres container and applies every migration to an empty database.
