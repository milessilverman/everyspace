## What changed

- Calendar sync now claims each feed with an expiring lease and applies a bounded snapshot in one database transaction under the property lock. It records failed attempts separately from successful observations. Missing bookings and older explicit revisions remain occupied until verified. Feed edits invalidate in-flight snapshots. The downloader restricts requests and redirects to approved HTTPS hosts. The parser rejects incomplete feeds and ambiguous ranges. Export uses a bounded single-value database snapshot and marks only a GET as a fetch request.
- Confirmation and amendment of Everyspace-managed inventory now pass the same locked capacity check as holds. The check includes cleanup, related spaces, unidentified calendar unit counts and pending provider operations. Changes to space settings cannot introduce conflicts with managed future bookings. Host-observed changes to external bookings are versioned, and recorded external overlaps remain visible. Host-side booking edits go through scoped database functions.
- The manual guard revalidates the listing, calendar link, property time zone and buffer after the network read. The Console presents a local hold or an instant-listing calendar observation and prompts the host to check the provider. Manual hold submissions reuse a command ID across retries. External booking changes are searchable by reference and can be recorded with verified new dates.
- The shared provider interface now has independent gates for webhook verification, reservation reads, availability checks and writes, approval, decline, cancellation, change, calendar, listing and health operations. An operation requires an implementation, recorded authorization, test validation and an enable decision. The Airbnb and Vrbo transports remain disabled. A failed worker job leaves its lease recoverable and other jobs can continue.
- Booking-email intake bounds message bytes, truncation risk, MIME depth and headers. It stores normalized booking details and a digest. Change, cancellation and refund notices go to review of the original booking. The input is host-submitted text or a saved message, with no private inbox connection.
- The Host Console separates feed retrieval, provider import, partner access and automatic approval. It shows connection errors, delayed reads, missing events, truncated views and conflicts. Calendar input includes the local offset when editing an hourly booking. The dashboard clears its data and cancels stale Edge requests on a host change. Its sign-in script has an integrity check. Removing a tracked listing removes its feed links and email reviews atomically and retains recorded occupancy. The management entry point and original simulator were both exercised.

## Findings

High severity indicates a risk to booking safety, tenant boundaries, or the integrity of authoritative records. Medium indicates a meaningful operational or usability gap with a workable fallback.

| Severity | Finding | Disposition |
| --- | --- | --- |
| High | An incomplete or shortened calendar could release future occupancy. Concurrent runs could overwrite a newer snapshot, and a failed fetch updated the apparent success time. | Fixed with transactional import, leases, separate attempt and success times, revision checks and review of disappeared events. |
| High | Calendar requests relied on broad URL acceptance, and host-writeable metadata could make a connection look healthy. | Fixed with a byte, redirect and time policy, approved exact hostnames and service-managed metadata. Custom and regional link hosts need approval before rollout. |
| High | Authenticated hosts had direct reservation write privileges. A trusted managed confirmation or amendment could bypass local occupancy validation. | Fixed with read-only host table grants, scoped write paths and a capacity check on managed confirmations and inventory edits. |
| High | A manual check could use a calendar link or property time zone that changed after the read began. A local hold could appear to be a provider clearance. | Fixed with a final configuration comparison under lock and separate host-review and instant-calendar outcomes. |
| High | REST row limits and calendar echoes could silently distort exported occupancy. Unknown unit demand also counted as one in some checks. | Fixed by a bounded snapshot with explicit failure, excluding imported closure echoes, ignoring unchanged Everyspace export IDs on import, and conservatively reserving the whole listing for unquantified calendar occupancy. Provider-rewritten IDs still need mapping. |
| High | Competing external confirmations can arrive between reads. Public calendars do not arbitrate bookings across providers. | Open by design. External observations are recorded and flagged. Atomic real-time cross-provider admission requires a verified contract controlling the affected inventory. |
| High | The staged API layer has no exercised real provider identity, signatures, authorization scopes, availability semantics or mutation recovery. | Kept disabled. Synthetic transport tests cover replay, stale evidence, timeouts, authoritative readback and recovery. Provider access, independent security testing and durable scheduling remain prerequisites. |
| Medium | A stale response or a hidden dialog could keep data on screen after an account transition. | Fixed with session-scoped reads and actions, explicit data reset and dialog cleanup. Tested using two actual local Auth accounts and PostgREST RLS. |
| Medium | Retries could create more than one manual hold. Listing removal could leave partially removed calendar links. | Fixed with command IDs and a transactional removal RPC. Existing outside booking facts remain visible. |
| Medium | External changes, extensions and refunds lacked a clear reconciliation path. | Confirmed manual or email booking changes and verified cancellations are recordable. | Medium | Provider support, successful data retrieval and the provider applying an update were easy to conflate. The Console could silently omit upcoming bookings. | Revised statuses, source-linked capability claims, failure and truncation indicators, calendar search, and provider-specific guidance. There are no verified staging alerts, throughput baselines or published operating limits for sustained failures. | Bounded batches and time budgets added, with sanitized failure logs. Supervised operations, alerting, queue recovery, load tests and retention work remain open. |

## Reservation guarantees and limits

The property lock serializes local holds and managed writes, including checks for a whole property's descendants. Time intervals are half-open and include configured cleanup. An independently configured driveway remains independent. Multiple units of the same inventory can be held when peak simultaneous usage fits. An incoming calendar with no unit count occupies the full listing for its recorded range.

A transaction that confirms or extends a managed booking through the guarded path must fit the locally recorded state at commit. External confirmations, verified host observations, and imports can reveal actual overlaps after that transaction. Everyspace reports those facts without cancelling an external booking. A feed GET establishes that a link was fetched. The recipient controls when it applies events. A delayed, malformed or stale feed cannot certify availability.

All-day occupancy uses the configured property time zone. Hourly ranges preserve the instant across midnight and daylight saving. For providers with only whole-day availability, a cleanup buffer can conservatively occupy part of an additional day. Recurring or duration-only calendar events currently require a supported provider format or manual handling. A missing iCal event in confirmed occupancy stays occupied until an explicit cancellation or direct provider verification.

## Before a supervised pilot

1. **Stage the migration and deploy the matching functions and Console together.** Check legacy upcoming rows, source and unit counts, property time zones, instant-listing configuration and exact feed hostnames on approved data. Apply to staging and verify database grants, stale calendar behavior, hold, export and email flows. Rehearse rollback with a restorable backup and a client and function version that matches the schema. The draft does not migrate production.
2. **Verify sources with opted-in hosts.** Use one Swimply pool and one Airbnb whole-property listing first. Test both documented calendar directions, independent parking, latency, provider redraws, changed or cancelled events, repeated local times, cleanup and redacted messages. Manually match the original booking when the email reference and iCal event ID differ. [Swimply pilot sequence](PROVIDER_AUDIT.md#swimply-strategy)
3. **Define monitoring, daily review and go/no-go thresholds.** Watch last successful feed read, backlog and oldest attempt, held or uncertain occupancy, duplicate notices, host-visible errors and unprocessed cancellations. Calendar sync starts no more than 120 reads on a run with eight in flight and a start budget. Benchmark database write and provider latency, then review Edge invocations, Postgres connections, storage, egress, retention and any required operator or mail fees before scaling.
4. **Request sanctioned access for prioritized providers.** Obtain Swimply's written position on booking and lifecycle access and owner authorization. Test authorized read-only messages or calendar transport first, with signed delivery, idempotency, backfill and reconciliation. Schedule a recovery worker and instrument timeouts before any write sandbox. Hold separate reviews for shared availability, corrections, cancellations, payments and certification. [Provider contacts and evidence](PROVIDER_AUDIT.md#founder-involvement)
5. **Expand automation only when the workflow can be verified.** Add a listing-scoped inbound email relay when approved. Use redacted fixtures, sender authentication, replay protection and review before acting. Prepare guest-message drafts from verified reservations and use explicit host review. Delivery needs provider-authorized messaging, scoped credentials and idempotency. Budget costs separately. Keep payments and refund automation outside the initial pilot.

Secrets belong in deployment secret storage. Treat anonymous outbound calendar links as bearer credentials and rotate them after unintended sharing. Logs should contain event class, timing, counts and safe correlation IDs, with no raw email, calendar link, guest details or provider token. Add authorization revocation and retention procedures before onboarding partners.
